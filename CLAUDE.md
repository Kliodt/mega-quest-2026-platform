# Quest Platform

Платформа для проведения игрового квеста. Команда ходит по корпусам и аудиториям, в каждой аудитории проходит одна игра, и её код открывает вопрос. Логика мини-игр живёт на фронтенде, выдача вопросов, проверка ответов, штрафы, таймер и рейтинг — на бэкенде.

Доменные правила и модель данных: `docs/plans/PLAN.md`. Правила работы с кодом: `CLAUDE.md`.

## Быстрый старт

```bash
cp .env.example .env          # поправьте секреты и порты при необходимости
docker compose up             # mongo + api + web
docker compose exec api npm run load-questions
docker compose exec api npm run load-teams
```

После запуска:

| Что | Адрес |
|---|---|
| Приложение команды | http://localhost:5173 |
| Swagger UI | http://localhost:3100/docs |
| Health-check | http://localhost:3100/api/health |

Данные квеста лежат в `packages/api/src/setup/` — отдельно от приложения, запускаются руками. Вопросы: `setup/questions/<gameType>.json`, файл на тип игры (`history.json`, `blitz.json`, …), внутри массив вопросов этого типа; формат — в README рядом с ними. Коды на дверях: таблица `setup/bindings.csv` (`code`, `room`, `location`). Команды: таблица организаторов `setup/teams.csv`, `load-teams` печатает названия и пароли в stdout. Этих файлов нет в git: в них правильные ответы и пароли, на чистой копии репозитория их кладут руками.

Загрузчики не мешают друг другу: `load-questions` заливает вопросы, ничего не пересоздавая, поэтому вопрос можно завести или поправить хоть посреди квеста. `load-teams` пересоздаёт команды и стирает весь их прогресс, включая созданные через админку, поэтому по ходу квеста его запускать нельзя.

## Переменные окружения

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `JWT_SECRET` | `change-me-in-dev-please` | подпись токенов команд |
| `ADMIN_TOKEN` | `change-me-admin-token` | заголовок `X-Admin-Token` для `/api/admin/*` |
| `API_HOST_PORT` | `3100` | порт API на хосте (в контейнере всегда 3000) |
| `WEB_HOST_PORT` | `5173` | порт фронтенда |
| `MONGO_HOST_PORT` | `27018` | порт Mongo на хосте (в контейнере 27017) |
| `CHOKIDAR_USEPOLLING` | `false` | включить, если hot reload не срабатывает |
| `MOCK_CODE` | не задан | тестовый код: открывает любую игру вместо её QR-кода и засчитывается как верный ответ на любой вопрос. При старте API пишет предупреждение в лог. Не задавать на реальном квесте |
| `WEB_DIST` | не задан | путь к собранному фронтенду: если задан, API раздаёт его сам (так работает прод) |
| `QUEST_DOMAIN` | — | домен для Caddy в проде |
| `QUEST_HOST_PORT` | `3300` | локальный порт приложения на сервере |

Порты на хосте смещены (3100, 27018), чтобы не конфликтовать с другими проектами. Внутри compose-сети сервисы общаются по именам: `http://api:3000`, `mongodb://mongo:27017/quest`.

## Команды разработки

```bash
docker compose up                        # поднять всё
docker compose exec api npm ci           # после изменения зависимостей (тома node_modules общие)
docker compose exec api npm run load-bindings  # залить коды на дверях из setup/bindings.csv
docker compose exec api npm run load-questions # залить вопросы из setup/questions/*.json (коды и команды не трогает)
docker compose exec api npm run load-teams    # пересоздать команды (стирает весь их прогресс)
docker compose exec api npm install      # доустановить пакеты в volume контейнера

npm test                      # тесты всех пакетов
npm test -w packages/api      # только бэкенд (домен + интеграционные на квест)
npm run typecheck             # tsc --noEmit по всем пакетам
npm run lint                  # ESLint
npm run format                # Prettier
```

Интеграционные тесты квеста поднимают локальный `mongodb-memory-server`, отдельная база не нужна.

Зависимости ставятся и на хосте (`npm install`) — для IDE, типов и запуска тестов вне контейнера.

## Админка

Открывается по адресу `http://localhost:5173/admin`, вход по значению `ADMIN_TOKEN` из `.env`. Токен хранится в браузере и уходит в заголовке `X-Admin-Token`; если сервер его отклонит, админка вернёт на страницу входа.

- **Команды** — список со статусом, шагом маршрута, решёнными вопросами, временем и штрафами; создание команды с паролем и маршрутом, удаление.
- **Страница команды** — карта маршрута: по каждому вопросу время, поправки времени, число подсказок и попыток, по кнопке «Ответы» — все попытки команды и взятые подсказки. Ниже все поправки времени команды (автоматические за неверные ответы и подсказки и ручные штрафы, компенсации, прочее), любую можно отменить; форма ручной поправки: причина, секунды со знаком, шаг, комментарий. У каждого уже открытого вопроса есть кнопка «Вернуть сюда»: она стирает прохождение этого шага и всё, что было после, и ставит команду перед ним ждать код. Ручные штрафы и бонусы при этом остаются. Дальше смена имени и пароля (смена пароля разлогинивает команду), редактор маршрута и кнопки сброса прогресса и удаления.
- **Вопросы** — все вопросы с типом игры, аудиторией и правильными ответами.

Маршрут проверяется сервером теми же правилами, что при загрузке данных. У команды, которая уже начала, пройденные шаги заблокированы, менять можно только хвост.

## Как добавить новый вопрос

Новый вопрос существующего типа кода не требует: допишите его в массив `packages/api/src/setup/questions/<gameType>.json` (`gameType`, `location`, `roomNumber`, содержимое и ответы — формат в `setup/questions/README.md`), выполните `docker compose exec api npm run load-questions` и укажите его аудиторию в маршруте команды (в админке или в `setup/teams.csv`).

## Как добавить новый тип игры

Роуты для команды у всех типов общие и живут в core: `GET /quest/question`, `POST /quest/hint`, `GET`/`PUT /quest/state`, `POST /quest/answer`. Читает и пишет вопросы тоже core — коллекция `questions` одна на все типы. Тип игры не объявляет эндпоинтов, а реализует контракт `GameTypeDefinition` (`packages/api/src/games/types.ts`): какие поля есть у вопроса сверх базовых (`extraFields`), как обернуть документ в `GameQuestion` (подсказки, штраф за ошибку, публичный `content`, `checkAnswer`), как показать вопрос организатору и, если нужно, как достроить его при загрузке данных. Форму `content`, `answer` и `state` core передаёт как `unknown`.

**Текстовая игра.** Если вопрос — текст, а ответ — строка, ничего описывать не нужно: это умолчания core, и тип занимает одну строку:

1. Добавьте значение в `GameType` (`packages/shared/src/enums.ts`).
2. Создайте `packages/api/src/games/<type>/index.ts`: `export const <type>GameType: GameTypeDefinition = { gameType: GameType.<TYPE> }`. Дальше можно добавить поля вопроса (`extraFields`) и переопределить `toPublicContent`, `checkAnswer`, `toAdminContent`, `toQuestionData`.
3. Зарегистрируйте его в `packages/api/src/games/registry.ts` и на фронте в `packages/web/src/games/registry.tsx`. Обе карты — `Record<GameType, …>`, новый тип без записи не компилируется.
4. Заведите вопросы нового типа в `packages/api/src/setup/questions/<gameType>.json`: содержимое лежит в полях `html` (текст, он же разметка) и необязательном `data` (произвольный JSON механики).

**Свой тип с нуля.** Если механика другая (картинка, сетка, несколько полей), объявите свои поля в `packages/api/src/games/<type>/schema.ts` и передайте их фабрике через `extraFields` (при необходимости реализуйте `GameTypeDefinition` целиком: `toGameQuestion`, `toAdminContent`, `toQuestionData`, `onStateUpdate`), а формы `content`, `answer`, `state` и админского вопроса опишите в `packages/shared/src/games/<type>.ts`. На фронте зарегистрируйте `WebGameTypeDefinition { label, Content, AttemptView, AdminQuestions }`: `Content` получает готовый `QuestionViewDto` и колбэки core `onSubmit(answer)` и `onSaveState(state)`, подсказки рисует core. Добавьте интеграционные тесты в `packages/api/test/<type>.test.ts`.

Правильный ответ хранится только в документе вопроса и никогда не уходит клиенту.

## Деплой на сервер

Прод — три контейнера: `mongo`, `app` (API вместе с собранным фронтендом) и `caddy`, который
держит https и проксирует всё на приложение. Наружу смотрит только Caddy; приложение слушает
`127.0.0.1:3300` — чтобы проверять с самого сервера. Всё описано в `docker-compose.prod.yml`
и `Dockerfile`, дев-окружение (`docker-compose.yml`) остаётся как было.

**Камера работает только по https**, поэтому сканер кодов на телефоне заведётся лишь после
того, как Caddy выпишет сертификат.

1. Направить A-запись домена на сервер и открыть на фаерволе 80 и 443.
2. Забрать проект и положить рядом данные, которых нет в git:

   ```bash
   # на сервере
   git clone <repo> quest_platform && cd quest_platform

   # с рабочей машины: секреты и всё, чего нет в git (список — в deploy/server-files.txt)
   scp deploy/.env.production сервер:~/quest_platform/.env
   rsync -avr --partial --progress --files-from=deploy/server-files.txt ./ сервер:~/quest_platform/
   ```

   Список `deploy/server-files.txt` — это таблицы команд и кодов, вопросы и ролики Яндекса,
   всего около 730 МБ, из них 693 МБ ролики. Ничего лишнего (`node_modules`, `.git`, сборки)
   не едет: остальное приезжает git-клоном. Сжатие (`-z`) для роликов не нужно — они и так
   сжаты, а `--partial` даёт продолжить прерванную заливку.

   Вопросы и таблицы попадают в образ (загрузчики запускаются в контейнере), а ролики Яндекса
   в образ не кладутся — они монтируются в контейнер как том.

3. Поднять и залить данные:

   ```bash
   docker compose -f docker-compose.prod.yml up -d --build
   curl -s localhost:3300/api/health                                   # {"ok":true,"mongo":true}
   docker compose -f docker-compose.prod.yml exec app npm run load-all -w packages/api
   ```

   `load-all` стирает прохождение команд: по ходу квеста запускают только `load-questions`,
   `load-bindings` или `load-locations` — они прогресс не трогают.

4. Открыть `https://<домен>`, войти любой командой, проверить сканер с телефона. Убедившись,
   что https работает, можно включить HSTS — строка закомментирована в `deploy/Caddyfile`.

Выкладка новой версии — `docker compose -f docker-compose.prod.yml up -d --build app`:
контейнер закрывается по `SIGTERM` сам, база и сертификаты живут в томах и переживают
пересборку. Логи и состояние:

```bash
docker compose -f docker-compose.prod.yml logs -f app   # запросы и вход команд
docker compose -f docker-compose.prod.yml ps            # healthcheck раз в 30 секунд
```

Бэкап базы: `docker compose -f docker-compose.prod.yml exec mongo mongodump --archive --db quest > quest-$(date +%F).archive`.

### Переезд с тизера

Тизер и квест живут на одном сервере и делят домен: 80 и 443 занимает Caddy того, кто
запущен, поэтому сначала гасим тизер, потом поднимаем квест. Новый Caddy выпишет на тот же
домен свой сертификат — это один повторный выпуск, в лимиты Let's Encrypt укладывается.

```bash
docker compose ls                                  # какие стеки сейчас подняты и откуда

# 0. Если Docker Hub с сервера не тянется («TLS handshake timeout»), берём mongo из зеркала:
#    в .env → MONGO_IMAGE=huecker.io/library/mongo:7 (проверено: зеркало отдаёт манифест)

# 1. Собрать образ, пока тизер продолжает работать: это самая долгая часть
cd ~/quest_platform
cp deploy/.env.production .env                     # если ещё не положили
docker compose -f docker-compose.prod.yml build

# 2. Поднять базу и приложение: 80 и 443 они не занимают, тизер не мешает
docker compose -f docker-compose.prod.yml up -d mongo app
curl -s localhost:3300/api/health                  # {"ok":true,"mongo":true}
docker compose -f docker-compose.prod.yml exec app npm run load-all -w packages/api

# 3. Сама подмена: тизер вниз, Caddy квеста вверх — занимает секунды
cd ~/quest_teaser && docker compose down
cd ~/quest_platform && docker compose -f docker-compose.prod.yml up -d caddy

# 4. Проверить
docker compose -f docker-compose.prod.yml ps                     # app → healthy
docker compose -f docker-compose.prod.yml logs caddy | tail -20  # виден выпуск сертификата
curl -sI https://mega-quest-2026.ru | head -3                    # 200 и https
```

Сборка идёт при живом тизере, поэтому домен недоступен только те секунды, пока один Caddy
сменяет другой. Данные заливаются до подмены: `load-all` стирает прохождение, и делать это
при играющих командах нельзя.

Откатиться на тизер, пока квест не начался:

```bash
cd ~/quest_platform && docker compose -f docker-compose.prod.yml down
cd ~/quest_teaser && docker compose up -d
```

База квеста остаётся в томе `quest_platform_mongo_data` и переживает и остановку, и откат.

## Подводные камни Docker

- `node_modules` лежат в named volumes, а не на хосте, и `docker compose up --build -V` их не обновляет: `-V` пересоздаёт только анонимные тома. После изменения зависимостей выполните `docker compose exec api npm ci` (тома общие для api и web), затем `docker compose restart api web`: watcher второго сервиса во время переустановки теряет модули и падает.
- Если правки файлов не подхватываются, поставьте `CHOKIDAR_USEPOLLING=true` в `.env` и перезапустите compose. По умолчанию polling выключен, чтобы не жечь CPU.
- Первый запуск тянет образы `node:24-alpine` и `mongo:7`; при обрыве загрузки повторите `docker compose pull`.


## Стек

- Монорепо npm workspaces: `packages/shared` (enum, TypeBox DTO), `packages/api`, `packages/web`. Всё на TypeScript. Актуальные мажоры библиотек; API сверять по документации (Context7) перед написанием кода.
- API: Node 24 (образ `node:24-alpine`), Fastify 5 + `@fastify/type-provider-typebox`, `@fastify/swagger` + swagger-ui (`/docs`), Mongoose 9, `@fastify/jwt`, `bcryptjs`, Vitest.
- Web: React 19, Vite 8, React Router 8, TanStack Query 5, SCSS-модули, `classnames` для склейки имён классов (шаблонные строки в `className` не используем). Без UI-библиотек: оформление своё, в `packages/web/src/ui/` (токены, компоненты, истории), смотреть — `npm run storybook -w packages/web`.
- ESLint flat config + Prettier в корне (`npm run lint`, `npm run format`). Без pre-commit хуков.
- **Прод — свой compose** (решение 2026-09-27): `docker-compose.prod.yml` + `Dockerfile` поднимают три контейнера — `mongo`, `app` (API раздаёт и собранный фронтенд по `WEB_DIST`) и `caddy` с https на домене из `QUEST_DOMAIN`. Приложение слушает только `127.0.0.1:3300`, ролики Яндекса не попадают в образ и монтируются томом, данные заливают из контейнера (`docker compose -f docker-compose.prod.yml exec app npm run load-all -w packages/api`). Порядок выкладки — в README, раздел «Деплой на сервер».
- Dev-окружение только через Docker: `docker compose up` (mongo, api на 3000, web на 5173, сторибук с UI-паком на 6006), проект смонтирован в контейнеры для hot reload.
- **Проверка с телефона — через туннель.** Камеру браузер даёт только на https и на localhost, поэтому сканер с телефона проверяется так: `ngrok http 5173`, и открыть выданный https-адрес. Отдельный туннель для API не нужен: дев-сервер сам проксирует `/api` и `/docs` в контейнер api. Домены туннелей уже разрешены в `vite.config.ts` (`allowedHosts`), свои добавляются через `WEB_ALLOWED_HOSTS`. Чтобы работал и hot reload, в `.env` дописать `WEB_HMR_CLIENT_PORT=443` и `WEB_HMR_PROTOCOL=wss`, затем `docker compose up -d web`.

## Глоссарий домена

- **Команда (team)** — основная сущность, логин по имени (строго) и паролю, JWT на 24 часа. Одна активная сессия: `sessionId` в документе команды и в JWT, новый логин выбивает остальные устройства (`auth__session_replaced`). Состояние команды хранится в её документе.
- **Вопрос (question)** — основная сущность содержания: и само задание, и места, где оно стоит. Поля: `rooms` (аудитории), `gameType`, содержимое (`html`, `data`), `acceptedAnswers`, `answerIsNextRoom`, `hasDynamicAnswer`, `shouldSendAnswer`, `wrongAttemptPenaltySeconds`, `hints` плюс поля своего типа игры. Отдельных сущностей «игра» и «аудитория» нет: все вопросы всех типов лежат в одной коллекции `questions`.
- **Вопрос опознаётся аудиторией (решение 2026-09-23).** Пара `location` + `roomNumber` и есть имя вопроса: на неё ссылаются шаги маршрута, по ней вопрос читают из базы и перезаливают из данных. Отдельного `slug` у вопроса нет. В коде пара — `RoomRef` (`shared/src/types/roomRef.ts`) и `RoomRefDto`, ключ словарей делает `toRoomKey` (`lomo/1216`); имя именно про аудиторию, потому что аудитория бывает и без вопроса — выход из корпуса. Задавать вопросы так проще: аудиторию организатор и так знает.
- **Один вопрос — много аудиторий (решение 2026-09-23).** Одна и та же игра стоит в нескольких аудиториях слово в слово, а ответ берётся из маршрута команды, поэтому вопрос описан один раз и перечисляет свои аудитории в `rooms: RoomRef[]`. Какую именно аудиторию отсканировала команда, помнит `questionStates.room` — из неё берутся номер в `QuestionViewDto` и карточка решённого шага.
- **Вариант для конкретных команд (решение 2026-09-26).** У варианта есть `teamSlugs` — команды, которым он предназначен (пусто = вариант общий). При вводе кода ядро сначала ищет вариант своей команды и только потом берёт общие (`utils/question/pickTeamQuestions`). Так устроены энциклопедия (три текста на 72 команды) и Яндекс (свой ролик и своё слово каждой). Что у команды есть свой вариант, проверяет валидатор маршрута — ошибка `room X has no question variant for this team` видна и при старте API, и в админке, и при заведении команды; загрузчик вдобавок ругается на `slug`, которых нет в базе. Если ни своего, ни общего варианта нет, ядро всё же выдаст чужой: ответ у вариантов один, и лучше чужой текст, чем аудитория без вопроса.
- **Команда опознаётся `slug`, а не именем (решение 2026-09-26).** Имя команды организаторы меняют, поэтому данные на команду ссылаются её `slug` из таблицы (`team_thwji`): он приходит из `teams.csv`, уникален и неизменен. Заведённой руками команде `createTeam` выдаёт случайный `team_xxxxx`. В админке организатор по-прежнему видит имена: `GET /admin/questions` переводит `slug` в имена перед отдачей.
- **Несколько вопросов в одной аудитории (решение 2026-09-24).** В аудитории бывает несколько вариантов вопроса — например телевизоры отправляют разные команды в разные аудитории. Маршрут по-прежнему называет только аудиторию, а какой из вариантов выдать, ядро решает при вводе кода: берётся **тот, что дольше всего свободен** среди подходящих команде. Занятость считается по `questionStates`: вариант занят, пока открывшая его команда не ответила; ни разу не выданный идёт первым, дальше — освободившийся раньше всех. Читает занятость `services/question/readQuestionUsage`, выбирает чистая `utils/question/pickFreeQuestion`, выданный вариант помнит `questionStates.questionId`. Счётчиков ротации и отдельной сущности варианта нет. **Куда идти, называет сам вариант (решение 2026-09-27):** если варианты разводят команды по разным аудиториям, шаг маршрута знает только аудиторию с кодом (телевизоры — площадка у лифта `lomo/1600`), а «Пройдите в аудиторию 1603…» стоит в `html` того варианта, чей ответ 3408; аудитории телевизоров кодов не имеют, платформе они неизвестны. Так же у Ягодного: вопрос выдаёт аудитория с QR, а решают его в 1316/1404/1405 — номер стоит первой строкой `intro`, по аудитории на вариант.
- **Привязка кода (binding)** — коллекция `bindings`: код на двери (8 символов `[a-zA-Z0-9]`, регистр учитывается) → `roomNumber` и `location`. Код говорит только про место; какой вопрос там открывать, решает маршрут команды. Коды печатаются в QR, команда их только сканирует: ручного ввода кода в окне сканера нет (решение 2026-09-27).
- **Таблица кодов (решение 2026-09-26)** — коды приходят одной таблицей `setup/bindings.csv` (колонки `code`, `room`, `location` кодом или названием корпуса; пометка рядом с номером — «107 (Б14)» — отбрасывается общим разбором `utils/csv/readRoomNumber.ts`, тем же, что у таблицы команд: платформа знает только номер, а ячейка целиком сохраняется в `roomTitle` и показывается организаторам на страницах кодов) и заливаются в коллекцию `bindings` своей командой `npm run load-bindings`, как команды. В вопросах кодов больше нет: один источник. Публичный `GET /api/pub/bindings/:code` читает ту же коллекцию и отдаёт аудиторию с корпусом — им пользуется страница организаторов `/pub/bindings`: навёл камеру на дверь, увидел номер аудитории.
- **Корпуса**: `lomo` Ломоносова, `cronva` Кронверкский, `birja` Биржа, `chaika` Чайка, `griva` Гривцова.
- **Тип игры (`gameType`)** — механика в `api/src/games/<type>/`: какие поля есть у вопроса сверх базовых, что из него видит команда и как проверяется ответ. Вопросов одного типа может быть сколько угодно.
- **Маршрут (`sequence`)** — заранее заданная линейная машина состояний команды. Шаги трёх видов (`StepKind`): `LOCATION_TRANSITION` (переход между корпусами, время стоит; первый шаг всегда такой), `ROOM_TRANSITION` (переход между аудиториями внутри корпуса, время идёт), `QUESTION` (список аудиторий допустимых вопросов, `options: RoomRef[]`, обычно одна, все в одном корпусе). Переходы и вопросы чередуются; маршрут заканчивается вопросом либо финишной аудиторией. Маршрут проверяется `validateSequence` при загрузке данных, при старте API и по кнопке в админке (`GET /admin/validation` → какие команды не сходятся и почему; та же проверка, что на старте).
- **Аудитория выхода из корпуса (решение 2026-09-23).** У `LOCATION_TRANSITION` тоже бывают `options` — аудитория, до которой команда доходит, не покидая корпус, и скан кода на её двери закрывает последний вопрос корпуса: ответ засчитан, время остановлено, началась пауза на дорогу. Вопроса в этой аудитории нет, только код в `bindings`; у первого шага маршрута выхода нет, закрывать нечего. **Квест закрывает последний ответ (решение 2026-09-27, заменяет скан финиша от 2026-09-24).** Ответив на последний вопрос маршрута, команда сразу финиширует: впереди одни переходы, сканировать нечего (`acceptAnswer` → `finishTeam`, проверка `utils/sequence/hasQuestionsAhead.ts`). Вместо перехода открывается финишный экран: благодарность, итоговое время, время прохождения и штрафы; ни «следующего корпуса», ни ввода кода там нет. Достижение за последний ответ не выдаётся — их ровно столько, сколько заданий в маршруте. Отсюда общее правило: **ответ-аудитория ведёт в ближайшую аудиторию маршрута** — следующий вопрос внутри корпуса или выход в конце корпуса (`utils/sequence/getNextRooms.ts`, одно место и для валидатора, и для вычисляемого ответа). Валидатор требует, чтобы эта аудитория была в том же корпусе, что и вопрос: иначе команда шла бы в другой корпус с идущим временем.
- **Состояние команды** — только `currentStepIndex`. Вид текущего шага говорит, ждём ли код и идёт ли время. Статус (не начали / идут / закончили) и время выводятся из индекса и меток в `questionStates`, отдельно не хранятся.
- **Открытие вопроса** — по коду из `bindings` получаем аудиторию и корпус, сверяем её с аудиториями следующего шага маршрута и открываем стоящий там вопрос; если их несколько, берётся дольше всех свободный. Если подходящей аудитории нет, код неверный. Тестовый код (`MOCK_CODE`) открывает первую аудиторию шага.
- **questionStates** — одна общая коллекция состояний пар команда-шаг: `room` (отсканированная аудитория), `questionId` (выданный вопрос), `questionSnapshot` (снимок вопроса, сделанный при открытии), попытки, подсказки, `openedAt`/`answeredAt`. Попытки и подсказки — журнал фактов без секунд.
- **Поправка времени (`timeAdjustment`, решение 2026-09-21)** — единый механизм для штрафов за неверные ответы и подсказки, ручных штрафов и компенсаций. Хранится массивом `timeAdjustments` в документе команды: `{ _id, timeAdjustmentSeconds, type: TimeAdjustmentType, createdAt, comment, stepIndex }`. Знак секунд задаёт направление (`> 0` штраф, `< 0` бонус), `type` — только причину (`WRONG_ANSWER`, `HINT`, `PENALTY`, `COMPENSATION`, `OTHER`); согласованность знака и типа проверяет только админская форма. Нулевые поправки не записываются. Отдельной коллекции штрафов нет; таймер, рейтинг, карточки шагов и история команды считаются по этому массиву.
- **Таймер** — от открытия первого вопроса до ответа на последний, минус паузы между корпусами, плюс сумма поправок времени. Считается на бэкенде чистой функцией `toTimerDto`; клиент тикает от `serverNow`.
- **Подсказки** — строго по порядку, каждая со своим штрафом; сколько их и какой штраф, задаёт сам вопрос (число подсказок любое). Неверные попытки не ограничены, штраф за попытку задан в вопросе. Core записывает попытку или подсказку в `questionStates` и поправку времени в команду (`recordTimeAdjustment`). Нормализация текстового ответа: только trim, схлопывание пробелов, нижний регистр.
- **Маршрут на экране** — карточки, соединённые линией: карточка вопроса и карточка перехода между корпусами с названием корпуса; переход между аудиториями карточки не имеет. **Номер аудитории есть только у решённого вопроса** (`roomNumbers: null` у остальных): ответом бывает номер следующей аудитории, и карта не должна его раскрывать. Исключение — **переход между аудиториями одного корпуса и финиш** (решение 2026-09-24): пока команда на `ROOM_TRANSITION`, аудитория следующего шага видна и в карточке, и на экране ввода кода; на финишном шаге так же видна его аудитория. Куда идти прямо сейчас, говорит поле `nextRoomNumbers` в `ProgressDto` — по нему же фронт решает, открывать ли следующий вопрос тем же кодом. На переходе между корпусами оно пустое: сначала команда добирается до корпуса. Второй способ узнать аудиторию — `shouldSendAnswer` у вопроса, ответ которого и есть аудитория: тогда она приходит в `answers` вместе с вопросом. Решённое задание на карте показано строкой «аудитория и время», под ней поправка времени и число подсказок, справа — стикер достижения; номер задания подписан только у непройденных. Команда видит бегущий таймер и сумму поправок времени под ним, по клику — их историю. Рядом с кнопкой подсказок стоит квадратная кнопка поддержки — ссылка на телеграм организаторов (`components/SupportButton.tsx`). После скана самого первого кода, до открытия задания, показывается приветствие про 7,5 часов (`components/WelcomeCard.tsx`); что команда его видела, помнит `localStorage` этого устройства. Экраны команды разделены: ввод кода и финиш на `/`, открытое задание на `/question`, карта маршрута на `/map` (`pages/QuestLayout.tsx` держит шапку и грузит прохождение).
- **Содержимое вопроса (решение 2026-09-21)** — пара `html` и `data` прямо в документе, без вложенного объекта. `html` — текстовая часть: обычный текст тоже разметка, отдельного поля под него нет, и рисуется он как разметка (содержимое пишут организаторы в `data/`, источник доверенный). `data` — произвольный JSON для механики игры, у текстовых полей его нет. Так же устроены подсказка (`{ html, data?, penaltySeconds }`) и принимаемый ответ (`{ html, data? }`). Сравнение ответа и показ идут по `html`.
- **Снимок вопроса (решение 2026-09-23).** При открытии вопроса ядро кладёт в `questionStates.questionSnapshot` весь документ вопроса с уже посчитанными ответами, и дальше команда работает только с ним: `GET /quest/question`, проверка ответа и подсказки читают снимок, а не коллекцию вопросов. Поэтому правка вопроса или маршрута не меняет открытую игру, а откат шага выдаёт вопрос заново.
- **Флаг `shouldSendAnswer` (решение 2026-09-23)** — ответ уходит команде вместе с вопросом, полем `answers` в `QuestionViewDto`. Так устроены игры, которые прячут ответ своей механикой: блиц показывает номер следующей аудитории внутри викторины, и как именно он спрятан, знает только фронт. У остальных вопросов `answers` пустой, правильный ответ клиенту не уходит.
- **Два флага ответа.** **`answerIsNextRoom`** — ответ на вопрос это номер следующей аудитории команды. **`hasDynamicAnswer`** — этот номер подставляет ядро по маршруту в момент открытия, поэтому своих `acceptedAnswers` у вопроса нет. Отсюда три допустимых сочетания: обычный ответ (оба флага сняты), заранее известный ответ-аудитория (`answerIsNextRoom`, номер приходит из реального мира — код на стене, кадр в ролике — или маршрут после вопроса ветвится) и вычисляемый ответ (оба флага). `hasDynamicAnswer` без `answerIsNextRoom` невозможен: ядро подставляет именно аудиторию. Маршрут проверяется в обоих случаях: у заранее известных ответов каждый обязан быть аудиторией одного из вопросов следующего шага, у вычисляемого после вопроса обязан идти ровно один вопрос (ветвление запрещено — непонятно, какую аудиторию считать ответом).
- **Аудитория без кода — не шаг маршрута (решение 2026-09-26).** Команда открывает вопрос только сканом кода на двери, поэтому аудитория без кода шагом быть не может. Так устроено Ягодное: ответ команда набирает руками, оставаясь на шаге аудитории с QR, а 1316/1404/1405 из таблицы шагами не становятся. В маршрут такие аудитории не попадают — колонка таблицы вида `1316→2101` на Кронверкском шага не даёт (`setup/toTeamData.ts`), в отличие от Ломоносова, где справа стоит вопрос с кодом (`1603→3408`).
- **Гугл-формы во весь экран (решение 2026-09-27).** Форма притворяется чужим сайтом, поэтому платформы на экране нет: флаг `fullscreen` в реестре игр фронта убирает и шапку с таймером (`QuestLayout`), и рамку вопроса (`QuestionCard`). Обратно — кнопка «Made with Megabattle» в правом нижнем углу, включается после первой отправки формы; она открывает окно платформы (`GoogleFormsPanel`): таймер с поправками, подсказки и сканер кода. У каждой команды свой вариант вопроса (`teamSlugs`): своё описание формы (`html`) и своя тема чата (`topic` — единственное поле типа сверх базовых), иконка темы берётся из `web/public/formIcons/<тема>.png` и стоит в шапке формы. Шапку фронт собирает сам: фон `games/form.png`, «Квест» по центру, иконка в левом верхнем углу. Подсказки у всех общие, ответ вычисляемый — он совпадает с колонкой «Ответ» исходной таблицы.
- **Ответ по открытой ссылке (решение 2026-09-26).** У соцсетей ответ задан заранее и один на всех (`SocialNetworksAnswer.CONFIRMED`, он же в `acceptedAnswers`), аудиторией он не является и поля ввода у вопроса нет. Засчитывает задание переход по ссылке из ролика на открытую страницу `/pub/confirm_video`: с устройства команды она сама отправляет ответ, без входа — просит открыть ссылку там, где команда вошла. Если открыто другое задание или никакого, ответ не отправляется: иначе переход не вовремя стоил бы команде штрафа.
- **Достижения (решение 2026-09-26, дополнено 2026-09-27)** — **первое достижение даётся за вход на платформу, дальше по одному за каждый засчитанный ответ**: в маршруте 12 заданий, поэтому к последнему из них (стикеры) у команды ровно 12 достижений. Порядок один на все команды и задан на бэкенде (`utils/achievement/toAchievementDtos.ts`), потому что из этих эмодзи собирается ответ на стикерах — тоже один на всех. Считаются от `solvedCount`, своего состояния нет: выдать дважды нельзя, порядок строгий, откат шага забирает достижение вместе с ответом. В `ProgressDto.achievements` уходят только полученные, будущие клиенту не отдаются. Свежее всплывает тостом под шапкой справа (выезжает сбоку, висит три секунды и уезжает обратно за край; по нажатию открывается окно достижения, а из него — кнопка на карту), а на карте видны все собранные достижения: за вход — отдельной строкой сверху, остальные справа от своих заданий, и любое по нажатию открывается крупно (`QuestionCardDto.achievement`). Картинки статикой в `packages/web/public/achievements/`, названия пока плейсхолдеры.
- **Дрампад засчитывает ответ сам (решение 2026-09-26).** У sound buttons ответ присылает железо в аудитории: `POST /pub/confirm_drum/:code`, где `code` — номер дрампада (`0`→3408, `1`→3412, `2`→4207, `3`→4213, `4`→4306). Роут открытый (у механизма нет ни входа, ни токена) и **лежит в корне, без префикса `/api`**: адрес зашит в железо (`routes/drum.ts`, в дев-режиме его проксирует `vite.config.ts`). Пустое тело с заголовком JSON допускается — железо шлёт именно так. Команду платформа вычисляет сама — по `externalAnswerCode` вопроса и открытому неотвеченному `questionStates` (`services/quest/confirmExternalAnswer.ts`); если вопрос открыт у двоих, ответ получает открывшая раньше. Дальше это обычный верный ответ (`acceptAnswer`, общий с `submitAnswer`), поэтому повтор сигнала ничего не меняет (`quest__no_waiting_team`), а неизвестный номер — `quest__unknown_external_code`. В ответе — кому засчитано: `{ teamName, roomNumber }`.
- **Флаг `waitsForExternalAnswer` (решение 2026-09-26)** — ответ засчитывает внешний механизм, а не экран задания: у sound buttons это кнопки в аудитории, у соцсетей — открытая страница `/pub/confirm_video`. Поле вопроса, а не свойство типа игры: флаг приходит команде в `QuestionViewDto`, и по нему **core** (`QuestionCard`) включает долгий запрос состояния `useQuestionStateWatch`. Сервер держит `GET /quest/state?since=<метка>` до четверти минуты и раз в секунду перечитывает открытый вопрос, поэтому засчитанный где-то ещё ответ виден сразу: вопроса больше нет, запрос падает с `quest__no_open_question`, фронт перечитывает прохождение и уходит на следующий шаг. Поля ввода у такого вопроса нет — sound buttons показывают задание и строку «Введите правильный ответ». В админке флаг виден значком волн в графе ответа.
- **Ответ — номер следующей аудитории.** В таких играх (история, блиц, гугл-формы, стикеры) команда не вводит ответ руками: она доходит до аудитории и сканирует её код. Общий web-компонент — `games/roomCodeAnswer/RoomCodeAnswer.tsx`, текст задания рисует сама игра; сама логика (код → номер → ответ → следующий вопрос) лежит в хуке `useRoomCodeAnswer`, поэтому игра может поставить сканер куда угодно. **История** вдобавок прячет номер в адресе страницы: он приходит команде общим механизмом `shouldSendAnswer` (в `answers` вместе с вопросом), а компонент подменяет адрес на `/question/<номер>`; своих полей у типа нет. Компонент игры получает номер по коду (`POST /quest/room-number`), отправляет его ответом (`onSubmit`) и, если ответ верный и квест не закончен, тем же кодом открывает следующий вопрос (`onEnterCode`). Поэтому ответом такого вопроса должна быть аудитория вопроса следующего шага, а сам шаг перечисляет в `options` все вопросы, куда ведут ответы предыдущего.
- **Ответ — исход игры на фронтенде.** У сапёра механика целиком на клиенте, а бэкенду важен только результат: `«0»` при подрыве мины (неверный ответ со штрафом, берётся за каждый подрыв) и `«1»`, когда открыты все безопасные клетки (верный ответ). Значения — enum `MinesweeperAnswer` в `shared`. **Поле целиком на фронте (решение 2026-09-26)**: размер (10×6, 10 мин) — константа `games/minesweeper/minesweeperSize.ts`. **Клетку команда выбирает сканированием (решение 2026-09-26)**: коды клеток расклеены в аудитории и лежат в базовых полях вопроса — `cells` (`{ code, row, col }`, источник — `setup/questions/minesweper.csv`), это отдельные коды, а не коды на дверях. Разбирает скан фронт: вся раскладка уходит команде вместе с заданием, чтобы не спрашивать сервер на каждый кадр. Проверить метку глазами можно на открытой странице `/pub/minesweeper` (она же `GET /api/pub/minesweeper/:code` → `{ row, col }`), как `/pub/bindings` для дверей. Экран — квадратная камера, поле с подсвеченной отсканированной клеткой и кнопки «Открыть» и «Поставить флаг»; флаги живут в состоянии прохождения, помеченную клетку открыть нельзя. **Три режима выбора клетки (решение 2026-09-27)**, кнопками наверху экрана (`minesweeperMode.ts`): «Вручную» — камеры нет, клетка выбирается пальцем на поле (выручает, когда коды не читаются); «Сканер» — камера сверху, поле под ней, клетку называет скан; «В кадре» — поле нарисовано прямо в кадре, отдельного поля под камерой нет. Режим живёт только на экране: ход игры один на все режимы и лежит в состоянии прохождения. **Поле достраивается к коду прямо в кадре (решение 2026-09-27)**: по четырёхугольнику найденного QR считается проекция плоскости стены (`toFieldQuads.ts`), и поверх камеры рисуются соседние клетки — открытые с цифрами, подорванные и с флагами (`MinesweeperOverlay.tsx`, рисование — `paintMinesweeperField.ts`). Сколько клеток уложится вокруг кода, задаёт константа `QR_TO_CELL_RATIO` в `minesweeperSize.ts` — сторона напечатанного QR в долях стороны клетки; её меняют вместе с печатью. Поле раскладывается по первому клику под него — `generateSolvableField.ts` (алгоритм из github.com/w29ahmed/minesweeper: решатель с правилами «цифра набрана» и подмножеств плюс перестановка мин по времени), чтобы поле проходилось рассуждением, без угадывания; клетка первого клика и её соседи всегда пустые. Разложенное поле вместе с ходом игры команда хранит в состоянии прохождения (`PUT /quest/state`), поэтому перезагрузка страницы мины не перемешивает. - **Admin** — всё непубличное под `/api/admin/*` за статическим токеном `ADMIN_TOKEN` в заголовке `X-Admin-Token`; web-админка под `/admin/*` (`packages/web/src/admin/`). Команды: список, карта команды с попытками, создание, изменение имени/пароля/маршрута, удаление, сброс, откат к началу шага-вопроса (`POST /admin/teams/:id/rewind`): стирает прохождение шага и всё, что было после, ставит команду на предшествующий переход, автоматические поправки этих шагов удаляет, ручные оставляет; вариант вопроса выдаётся заново по ротации. Ручные поправки времени — `POST /admin/teams/:id/time-adjustments`, отменить можно любую поправку, включая автоматическую (`DELETE /admin/teams/:id/time-adjustments/:timeAdjustmentId`). **Ответ за команду** — `POST /admin/teams/:id/answer` (кнопка «Засчитать ответ» у открытого вопроса на карте шагов): засчитывает открытый вопрос верным ответом и двигает команду дальше, попытка остаётся в журнале текстом «ответ засчитан организатором»; без открытого вопроса — `quest__no_open_question`. **Скан за команду** — `POST /admin/teams/:id/scan` (кнопка «Засчитать скан» у шага, который ждёт код, и у финишного перехода): открывает вопрос первой аудитории шага или закрывает квест на финише — тем же путём, что тестовый код; если вопрос уже открыт, ничего не меняет. Маршрут начавшей команды можно менять только после пройденных шагов (`team__route_prefix_locked`). Страница «Маршруты» — таблица организаторов с сервера: строка на команду, колонка на корпус в порядке обхода, внутри аудитории по шагам (считает `admin/utils/toRouteSegments.ts` из маршрута в `GET /admin/teams`). Коды на дверях — страница «Коды»: `GET /admin/bindings`, `POST /admin/bindings` (завести код или перенести в другую аудиторию; второй код на ту же дверь разрешён — сканируют любой, админка только предупреждает; аудиторию пишут как в таблице — «107 (Б14)», номер разбирается тем же `readRoomNumber`, пометка без номера — `binding__room_invalid`), `DELETE /admin/bindings/:code`. Коды клеток сапёра правятся так же, страница «Сапёр»: `GET /admin/cells`, `POST /admin/cells` (завести код или перенести на другую клетку, у клетки код один — `cell__taken`; аудитория называет вопрос — `cell__question_not_found`), `DELETE /admin/cells/:code`. Все вопросы с правильными ответами отдаёт `GET /admin/questions`: общая часть (корпус, аудитория, тип) от core, `content` — от `toAdminContent` типа игры; рендерят компоненты типа `AttemptView` и `AdminQuestions`.

## Правила проекта

- Вся логика выдачи вопросов, проверки ответов, штрафов, таймера и рейтинга — на бэкенде. Правильный ответ никогда не отдаётся клиенту. Логика самих мини-игр — на фронтенде.
- **Core и типы игр.** Core API (`/api/quest/*`, `/api/auth/*`, `/api/admin/*`) — весь квест, включая действия команды над открытым вопросом: `GET /quest/question`, `POST /quest/hint`, `GET`/`PUT /quest/state` (произвольный JSON промежуточного состояния; `GET` с `?since=<метка>` висит до четверти минуты и возвращается, как только состояние изменится — этим sound buttons ждут внешнего механизма), `POST /quest/answer`. Роуты одинаковы для всех типов; форму `content`, `answer` и `state` core передаёт как `unknown`. **Читает и пишет вопросы только core** — коллекция одна на всех. Тип игры — модуль `packages/api/src/games/<type>/`, экспортирующий `GameTypeDefinition` (`games/types.ts`). Обязателен только `gameType`, всё остальное — переопределения: `extraFields` (поля вопроса сверх базовых, core добавляет их в схему дискриминатором по `gameType`), `toPublicContent`, `checkAnswer`, `toAdminContent`, `toQuestionData`, `onStateUpdate`. **Умолчания живут в core**: вопрос текстовый, содержимое — само задание, ответ `{ text }` против `acceptedAnswers` с нормализацией (`utils/question/toGameQuestion.ts`, рядом `isAcceptedAnswer`, `toBasicQuestionContentDto`, `toBasicAdminQuestionDto`). Поэтому тип без своей механики — это одна строка: `export const xGameType: GameTypeDefinition = { gameType: GameType.X }`. `toQuestionData` достраивает вопрос из `data/` перед записью в базу. **Core знает конкретные типы ровно в одном месте — `games/registry.ts`**; прямой импорт из `games/<type>/` откуда-либо ещё в core запрещён правилом ESLint (папки данных игр `data/<gameName>/` исключение: им нужен тип вопроса). На фронте реестр `packages/web/src/games/registry.tsx`: `WebGameTypeDefinition { label, Content, AttemptView, AdminQuestions }`; `Content` получает `QuestionViewDto` и колбэки core, подсказки и попытки рисует core. **У каждого типа свой `Content` в `web/src/games/<type>/`**: на бэкенде вопросы могут храниться одинаково, но показывать их команде нужно по-разному. Общие блоки ответа лежат отдельно: `basicGame/TextAnswer.tsx` (ответ строкой) и `roomCodeAnswer/RoomCodeAnswer.tsx` (ответ сканированием кода аудитории). Пошагово — в README. Вопросы не меняются во время квеста.
- Внутренние детали ошибок не уходят клиенту: сообщения `ApiError` со статусом 500 заменяются на общее, подробности только в лог.
- **Сервисы и утилиты (правило 2026-09-21).** `packages/api/src/services/<модуль>/` — единственное место, где читают и пишут базу: метод сервиса сначала читает нужные документы (один раз, все вместе), затем считает через утилиты или сам, если вычисление уникально для него, затем пишет изменения. `packages/api/src/utils/<сущность>/` — чистые функции: получают уже загруженные объекты или их части, ничего не читают, не пишут и не мутируют, только вычисляют (`utils/progress`, `utils/timer`, `utils/timeAdjustment`, `utils/rating`, `utils/sequence`, `utils/team`, `utils/question`, `utils/errors`). Утилитам запрещено импортировать `mongoose` и что-либо из `services/` (правило ESLint); типы моделей импортировать можно. **Преобразование в DTO — тоже утилита**, лежит в `utils/<сущность>/` и называется `to<ИмяDto>` по типу результата: `toTeamDto`, `toProgressDto`, `toQuestionViewDto`, `toRatingDto`, `toAdminTeamDetailDto`, `toTimeAdjustmentDtos` для массива; в сервисах и роутах DTO руками не собирают. Следствие: в одном запросе документ читается один раз, а не заново в каждом вложенном вызове. То же деление внутри типа игры: `games/<type>/services` и `games/<type>/utils`.
- **Структура `packages/api/src/services` и `utils`.** Папка на модуль (`quest`, `openQuestion`, `auth`, `rating`, …) или на сущность в утилитах (`progress`, `timeAdjustment`, `team`, …), внутри — файл на каждую функцию публичного API модуля: имя файла совпадает с именем функции, файл экспортирует ровно одну функцию. Внутренние помощники, которые нужны только этой функции, живут в том же файле ниже неё без `export`; отдельный файл заводится, только когда функцию используют из нескольких мест или она тестируется напрямую. Общие для модуля интерфейсы и типы — в `types.ts` этой же папки, константы живут рядом с единственной использующей их функцией. Barrel-файлов (`index.ts`) в `services` нет: импортируем напрямую из файла нужной функции. То же правило действует внутри типа игры.
- **Глаголы в именах функций.** `read*` — прочитать из хранилища как есть (`readTeam`, `readOpenState`, `readQuestionBySlug`); `load*` / `set*` — записать данные в хранилище или кэш (`loadQuestions`, `useSetProgressCache`); `get*` — получить значение или результат, в том числе вычисленный (`getProgress`, `getRating`, `getCurrentStep`). Функция называется глаголом, а не существительным: не `currentStep`, а `getCurrentStep`. Слово «seed» не используем: стартовые данные лежат в `setup/`, скрипты — `load-bindings`, `load-questions` и `load-teams`.
- Все входы и выходы API — именованные TypeBox DTO из `shared`; никаких анонимных объектов.
- **Имена типов (как рекомендует документация Mongoose).** Сырой документ, то есть объект в базе, называется существительным без суффикса: `Question`, `Team`, `Binding`, `QuestionState`, `BlitzQuestion`; так же называются встроенные поддокументы: `QuestionField`, `Attempt`, `HintTaken`, `TimeAdjustment`, `SoundButton`. Гидратированный документ (то, что возвращает `findOne`) — `<Сущность>Document = HydratedDocument<Сущность>`: `QuestionDocument`, `TeamDocument`. Стартовые данные — `<Сущность>Data` (`QuestionData`, `MinesweeperQuestionData`), контракт API — `<Имя>Dto`. **Схемы Mongoose параметризуются сырым документом, а не DTO**: хранение и контракт клиента меняются по разным причинам, между ними стоит преобразование `to<ИмяDto>`. Экспортируем только то, что импортируют снаружи: сырой тип часто нужен лишь своему файлу (`Binding`, `QuestionState`), наружу уходит `<Сущность>Document`.
- **Роуты.** Защита и общие поля OpenAPI-схемы задаются на плагине роутов, а не в каждом роуте: `app.addHook('onRequest', app.adminAuth)` или `app.authenticate` в начале плагина и `routeSchemaDefaults` для `tags` и `security` (`plugins/routeSchemaDefaults.ts`). В опциях роута остаются только `summary`, `params`, `body`, `response`. Тест `routeGuards.test.ts` проверяет, что все роуты `/api/admin/*` и `/api/quest/*` закрыты.
- **Ошибки.** Ответ всегда `{ code: string, message: string, data?: object }`.
  - Код и сообщение хранятся вместе в константах по доменам: `packages/shared/src/errors/{common,auth,quest,team}.ts`, формат `{ code: 'домен__snake_case', message: '...' }`.
  - На каждую ошибку — свой подкласс в `packages/api/src/utils/errors/` с зашитым HTTP-статусом. Статусы берём из `http-status` (`httpStatus.CONFLICT`), голых чисел в коде нет, в том числе в ключах `response` схем роутов: `response: { [httpStatus.OK]: … }`.
  - **В месте броска не должно быть ни текстов, ни кодов, ни произвольных полей**: только `throw new WrongCodeError()`. Конструктор принимает лишь параметры-значения, например `new HintOrderViolationError(nextHintIndex)`.
  - Ошибки 5xx наследуются от `InternalApiError`: их контекст идёт в `logData` и пишется только в лог, клиенту уходят код и безопасное сообщение. Публичные `data` бывают только у 4xx.
  - Новая ошибка = константа в `shared` + класс в `api`. Нельзя собирать ошибку на месте.
- `ApiErrorCode` — тип, выведенный из констант (объединение литералов), а не enum: иначе код и сообщение пришлось бы держать в двух местах. Это единственное осознанное исключение из правила «enum вместо union-типов».
- В UI каждый запрос имеет состояние загрузки и обработку ошибки.
- Enum вместо union-типов. Без вложенных и многострочных тернарников. Без `await` в циклах (`Promise.all` над `map`), без `return await` вне `try/catch`, без оператора «запятая» (правила ESLint `no-await-in-loop`, `@typescript-eslint/return-await`, `no-sequences`, `no-nested-ternary`).
- **Загрузка данных живёт в `src/setup/` и отдельно от приложения** (решение 2026-09-26): там и файлы данных, и загрузчики, и их утилиты. Из проекта `setup` берёт только типы `shared`, модели Mongoose и чистые утилиты — сервисы, роуты, игры, конфиг и подключение к базе ему запрещены правилом ESLint (и обратно: приложение не импортирует `setup`). К базе подключается сам по `MONGO_URI`. Запускают загрузчики руками с консоли сервера, в рантайм они не входят.
- **Загрузчики не пересекаются** (решение 2026-09-21): каждый отвечает за свой набор коллекций, и по ходу квеста запускают только тот, что не стирает прогресс. `npm run load-all` гоняет их все по порядку (коды → тексты переходов → вопросы → команды) — этим поднимают данные с нуля, по ходу квеста он не годится: последним шагом стирает прогресс.
  - **Вопросы — JSON, файл на тип игры, вне git** (решение 2026-09-23): `setup/questions/<gameType>.json` (`history.json`, `blitz.json`, …), внутри массив вопросов одного типа, каждый со своими `location` и `roomNumber`; коды на дверях лежат отдельной таблицей. Файлы в `.gitignore`: в них правильные ответы, поэтому в репозиторий они не попадают, а на чистой копии кладутся руками. Заливает `npm run load-questions` (`setup/loadQuestions.ts`): пишет каждый вопрос по его аудиториям, коллекции не пересоздаёт, коды, команды и прогресс не трогает, поэтому вопросы добавляются и правятся по одному хоть посреди квеста. Незаданные поля берутся из умолчаний (задание без текста, без подсказок, без штрафа), проверяются корпус и аудитория, один вопрос на аудиторию, один тип игры на файл и сочетание флагов ответа; про аудиторию без кода загрузчик предупреждает. Формат — в `setup/questions/README.md`.
  - `npm run load-bindings` (`setup/loadBindings.ts`) пересоздаёт коды на дверях из `setup/bindings.csv`.
  - `npm run load-locations` (`setup/loadLocations.ts`) пересоздаёт тексты переходов между корпусами из `setup/locations.json`: запись это `location` (куда идёт команда), необязательный `from` (откуда; без него текст годится для любого перехода в этот корпус) и `html`, пустые пропускаются. Текст пары побеждает общий — так SideQuest стоит только на переходе между вторым и третьим корпусом (`lomo → cronva` у одних команд, `cronva → lomo` у других). Прогресс не трогает, поэтому текст правится хоть посреди квеста.
